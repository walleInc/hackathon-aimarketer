# Бизнес-логика AI-маркетолога

Документ описывает правила, которые система соблюдает всегда. Каждое правило помечено: **[есть]** — реализовано и покрыто
тестом, **[частично]** — работает в упрощённом виде, **[план]** — в доработках для коммерческого использования.

## 1. Роли и права

| Действие | Администратор (оператор) | Согласующий | Сотрудник |
|---|---|---|---|
| Создать компанию, настроить знания, бренд-кит, каналы, лимиты | ✅ | — | — |
| Пригласить сотрудников, отозвать доступ к каналу | ✅ | — | — |
| Поставить задачу агенту, задать вопрос | ✅ | ✅ | ✅ |
| **Одобрить / отклонить / вернуть на доработку** | ✅ | ✅ | ❌ |
| Видеть данные других компаний | ✅ (все) | ❌ | ❌ |

Операторы: постоянные задаются в `ADMIN_IDS` на сервере, остальных оператор добавляет и убирает в админке (раздел «Операторы», по Telegram ID).
Снятие роли действует сразу; бывший оператор с компанией остаётся её сотрудником без прав администратора. Нельзя убрать самого себя
и оператора из `ADMIN_IDS`. Уведомления об ошибках получают все операторы. **[есть]**

Привязка к компании — только по одноразовой ссылке-приглашению; обычный пользователь не может сменить компанию. **[есть]**

## 2. Жизненный цикл публикации

```
запрос → черновик → проверка бренда → на согласовании ─┬→ одобрено → публикуется → опубликовано
                                                        ├→ отклонено (конец)
                                                        └→ доработка → новая версия → снова на согласовании
```

1. **Публикация возможна только из «одобрено».** Любая другая попытка отклоняется. **[есть]**
2. **Одобрение привязано к версии.** Любая правка текста увеличивает версию и сбрасывает пост на повторное согласование,
   даже если он уже был одобрен. **[есть]**
3. **Ровно одна публикация.** Пост атомарно «захватывается» воркером; повторный запуск или перезапуск не создаёт дубль. **[есть]**
4. **Сбой публикации** → статус «ошибка», уведомление администратору, пост можно вернуть на согласование. **[есть]**
5. **Отклонённое и опубликованное не редактируются.** **[есть]**
6. Время публикации: сразу после одобрения или по расписанию (`scheduled_at`); планировщик подхватывает отложенные посты. **[есть]**

## 3. Подготовка материала (конвейер агента)

1. Агент получает сообщение на естественном языке и **контекст только своей компании**: профиль, тон, правила бренда,
   база знаний (до 8000 символов), последние 12 сообщений диалога. **[есть]**
2. Если в базе нет факта, агент не выдумывает, а просит его добавить. **[есть, проверено на реальной модели]**
3. **Проверка бренда перед согласованием:** второй вызов модели сверяет текст с правилами бренда и базой знаний; найденные
   нарушения исправляются автоматически, согласующий видит заметку «что исправлено». **[есть]**
4. **Изображение:** карточка в фирменном стиле (раздел 4) или, если включён `AI_IMAGES`, ИИ-картинка с логотипом. **[есть]**
5. Материал уходит согласующему в Telegram: текст, изображение, площадка, время публикации, заметка проверки. **[есть]**

## 4. Правила бренда в изображениях (из брендбука САЛАВАТСТЕКЛО)

| Правило брендбука | Как реализовано |
|---|---|
| Логотип только из оригинальных файлов, без искажений, обводок, поворотов | Логотип берётся из загруженных файлов, только масштабируется с сохранением пропорций |
| На светлом фоне — основной цвет, на тёмном — белый; чёрный только монохром | Вариант выбирается по яркости фона под логотипом |
| Не ставить логотип на границу контрастных элементов | Из четырёх углов выбирается самый ровный по яркости |
| Охранное поле и минимальный размер (110 px для блока) | Отступ ≈ 0,6 высоты логотипа; ширина не меньше 110 px |
| Шрифты: Intro Black (заголовки), Avenir Next Cyr (текст) | Берутся из бренд-кита компании |
| Только фирменная палитра | Основной цвет и палитра задаются в бренд-ките; карточка использует только их |
| Название бренда — «САЛАВАТСТЕКЛО» слитно, не отдельно от знака | Правило в промпте и в проверке бренда |

Ограничения: охранное поле приближённое (точная «высота буквы О» не вычисляется), правила применения дескрипторов
(Агидель, Волга, Каспий) и нестандартных носителей не автоматизированы. **[частично]**

## 5. Расходы и лимиты

- **Месячный бюджет токенов** на компанию (по умолчанию 300 000): при исчерпании агент перестаёт вызывать модель, отвечает
  пользователю и **один раз в месяц** уведомляет администратора. **[есть]**
- **Дневной лимит материалов** (по умолчанию 5): защита от спама и неконтролируемых расходов. **[есть]**
- Расход по компаниям виден в админке и в `/api/admin/usage`. **[есть]**
- Бюджет проверяется перед каждым обращением к модели, включая «Доработать» (до смены статуса поста, чтобы он не застревал). **[есть]**
- Токены берутся из ответа провайдера (`usage`: вход, выход, всего). Если провайдер `usage` не вернул, учёт занижается. **[есть]**
- Стоимость в долларах: вход и выход считаются по тарифу модели (`LLM_PRICE_INPUT_PER_M`, `LLM_PRICE_OUTPUT_PER_M`, $ за 1 млн токенов);
  если провайдер сам возвращает цену, берётся она. Расход и использование бюджета видны на дашборде. **[есть]**
  Пересчёт в рубли и фактические счета провайдера не автоматизированы. **[план]**

**Оценка затрат одного AI-маркетолога в месяц:**
`стоимость = (материалов в месяц × токенов на материал) × цена за токен + хостинг`.
Измерено: один материал с проверкой бренда и одной доработкой ≈ 2–4 тыс. токенов. При 30 материалах в месяц это ≈ 60–120 тыс.
токенов — внутри бюджета по умолчанию. Хостинг: один небольшой VPS на несколько компаний.

## 6. Изоляция компаний (мультитенантность)

- `company_id` есть в каждой клиентской таблице; пост по идентификатору ищется только в компании пользователя. **[есть]**
- Знания, история диалога, бренд-кит, задачи, расходы и журнал разделены по компаниям; тесты проверяют, что компания B не видит
  ни посты, ни знания, ни память компании A. **[есть]**
- Токены соцсетей хранятся зашифрованными и никогда не возвращаются через API. **[есть]**

## 7. Расписание и автономность

- Регулярная задача: «раз в N часов подготовь материал по теме X». Запуск фиксируется **до** выполнения — повтор после сбоя не дублирует. **[есть]**
- Всё состояние (задачи, статусы, очередь публикаций) в БД: после перезапуска работа продолжается. **[есть]**
- Ошибки задач и публикаций уходят администратору в Telegram. **[есть]**

## 7.1. Файлы контекста организации (Yandex Object Storage)

- Файлы организации лежат в бакете по пути `{organization_id}/{файл}`; загрузка и удаление — в админке (вкладка «Знания»).
  Форматы: TXT, MD, CSV, JSON, HTML, PDF, DOCX, до 10 МБ. Имя файла очищается от путей: выйти за префикс своей организации нельзя. **[есть]**
- При запросе к AI текст файлов берётся из S3 и добавляется к базе знаний (не более `CONTEXT_FILES_LIMIT` символов).
  Организация A не видит файлы организации B. Недоступность S3 не ломает ответ агента. **[есть]**

## 7.2. Redis

| Назначение | Как используется |
|---|---|
| Кэширование | системный промпт (профиль бизнеса, правила бренда, знания, файлы) и извлечённый текст файлов; сброс при любом изменении, иначе TTL 5 минут |
| Rate limiting | запросы к AI: `AI_RATE_LIMIT_PER_MIN` на организацию и `AI_RATE_LIMIT_PER_USER_PER_MIN` на пользователя |
| Временное состояние | состояние диалога в Telegram (например, «жду комментарий к доработке») с TTL 24 ч |
| Distributed locks | публикация поста (`publish:{id}`) — два экземпляра не опубликуют один пост дважды |
| Pub/Sub | канал `aim:events`: смена статуса поста, изменение контекста организации |
| Очереди | BullMQ (см. ниже) |

Без `REDIS_URL` (разработка, тесты) используется встроенный in-memory Redis, а задачи выполняются сразу в процессе. **[есть]**

## 7.3. Очереди BullMQ

| Очередь | Задачи |
|---|---|
| `document-processing` | извлечение текста из загруженных файлов |
| `ai-generation` | регулярные задачи агента; параллелизм `AI_CONCURRENCY`, не более `AI_ORG_CONCURRENCY` на организацию |
| `publishing` | публикация одобренных постов; отложенный запуск в `scheduled_at`; 4 попытки с нарастающей паузой |
| `scheduled-tasks` | периодический тик (поиск регулярных задач и просроченных публикаций) |
| `analytics` | почасовая сводка по организациям (`GET /api/admin/analytics`) |
| `notifications` | уведомления согласующим и администраторам в Telegram, 5 попыток |
| `moderation` | анализ входящего текста: метка и черновик ответа **[обработчик есть, источника сообщений пока нет]** |

Состояния задач (waiting / active / completed / failed / delayed) — `GET /api/admin/queues`.
Об окончательном сбое публикации администратор узнаёт один раз, после последней попытки. **[есть]**

## 8. Журнал и аудит

Фиксируются: создание и правки компании, знаний и бренд-кита, подключение и отзыв каналов, вступление сотрудников, каждое
решение по материалу, публикации и ошибки, исчерпание бюджета. **[есть]**

## 9. Что нужно для коммерческого использования **[план]**

- Подключение через аккаунт ChatGPT (критерий №12) — требует отдельной проверки способа авторизации и условий использования.
- VK и MAX; статистика соцсетей и отчёты с рекомендациями; мониторинг комментариев с разрешением на автоответы.
- Загрузка PDF/сайта в базу знаний с поиском по фрагментам, а не по всему тексту.
- Миграции БД (Alembic), резервное копирование, роли внутри команды клиента шире трёх.
- Биллинг: тарифы, пересчёт токенов в рубли, счета клиентам.
- Автоматическая проверка изображений на соответствие брендбуку для загружаемых клиентом фото.
