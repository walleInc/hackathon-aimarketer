# Кабинет маркетолога: анализ ТЗ и предложение реализации

Дата: 14 ноября 2026. Базовая версия: `main`, `eb26999`.
Статус: исходный анализ и согласованное предложение. Реализация выполнена после
подтверждения пользователя; актуальное описание — [marketer-cabinet.md](marketer-cabinet.md).

## 1. Зафиксированные решения пользователя

- Кабинет доступен администратору компании и сотрудникам своей компании.
- Первый этап: Telegram и веб-поиск. VK и MAX — следующий этап.
- Раздел заявок и продаж предусмотрен, до подключения источника — «Нет данных».

## 2. Границы задачи по ТЗ

Прочитано исходное ТЗ целиком, четыре страницы. Наш основной объём — п. 3.2
«Изучение бизнеса» и п. 3.6 «Маркетинговая аналитика». С ними связаны контент-план
из п. 3.3, доступная статистика из п. 3.4, расписания и уведомления из п. 3.1,
правила согласования из п. 3.5 и изоляция компаний из разделов 4–5.

Мини-апп — рабочее место для просмотра, настройки и запуска анализа. Telegram
сохраняется как основной канал общения и согласования, согласно ТЗ.

Обязательный сценарий хакатона в разделе 6 прежде всего проверяет подготовку,
согласование и реальную публикацию контента. Аналитика расширяет этот цикл;
её реализация не должна нарушать публикации, историю и автономные задачи.

## 3. Текущая архитектура

- Frontend: React 18, TypeScript, Vite, Tailwind, shadcn/Radix, Zod, react-hook-form.
  Структура FSD: app → pages → widgets → entities → shared.
- Backend: FastAPI, SQLAlchemy async, SQLite для локальной работы, PostgreSQL в production.
- Telegram: aiogram для бота и публикаций, Telethon для статистики через сессию аккаунта.
- Автономность: APScheduler без Redis; BullMQ, очереди, блокировки и кэш с Redis.
- Знания: профиль, текстовые записи и файлы компании из S3; контекст передаётся LLM.
- AI: сменяемые провайдеры stub/openai/chatgpt_account; последний — заглушка.
- Развёртывание: Docker, PostgreSQL, Redis, Caddy, GitHub Actions.

Зависимости локально не установлены: нет backend/.venv и frontend/node_modules,
в системном Python отсутствуют pytest, FastAPI, aiogram и Telethon. Полный прогон
тестов и сборка не выполнялись. AST-проверка 56 Python-файлов: синтаксических ошибок нет.
Работу внешних сервисов и production эта проверка не подтверждает.

## 4. Соответствие требованиям

| Требование | Что есть в коде | Что нужно в нашей части |
|---|---|---|
| Изучение компании | Профиль, знания, документы в контексте AI | Структурированные продукты, аудитории, преимущества, цели; ссылки на основания |
| Изучение рынка | Тип задачи market: Tavily → LLM → текст и источники в TaskRun | Отдельный экран, параметры рынка/географии, история, структурированные выводы |
| Конкуренты | Упоминание в общем поисковом запросе и отчёте market | Список конкурентов, сайты/каналы, отдельный анализ каждого и сравнение |
| Маркетинговая стратегия | Общий контекст компании | Версии стратегии: цели, аудитории, позиционирование, каналы, рубрики, KPI |
| Контент-план | Создание отдельных постов и регулярные задачи | План тем и форматов, связь со стратегией и гипотезами |
| Сбор показателей | Реакции из обновлений бота; ручные показатели постов; отдельный сбор Telethon | Единая модель данных и сводка, синхронизация, покрытие и свежесть |
| Эффективность публикаций | post_analytics: суммы, доля реакций, рекомендации | Фильтр канала, сопоставимые периоды, детализация и история измерений |
| Результативные форматы | has_image; эвристика лучшего поста; текст AI | Рубрика/формат, объём выборки, сравнение по измеримым результатам |
| Гипотезы | Текст советов в AnalyticsAdvice и результатах задач | Карточки, основания, целевая метрика, критерий успеха, срок и статусы |
| Регулярные отчёты | Запуски statistics/market/recommendations по расписанию | Единый отчёт: показатели → выводы → действия, архив и уведомление компании |
| Заявки и продажи | Модели и источника нет | Состояние «Нет данных», описание требуемого источника |
| Изоляция компаний | company_id, контекст авторизации, тесты | Сохранить для всех новых таблиц, задач и API |
| Согласование | Версии постов, повторное согласование после правок | Сохранять цепочку при переходе от гипотезы к контенту |

## 5. Найденные проблемы и ограничения

### Блокирующий дефект подключения API

`backend/app/routers/analytics.py` содержит GET /api/analytics/posts,
PUT /api/posts/{post_id}/metrics и POST /api/analytics/posts/recommendations.
Но `backend/app/main.py` не импортирует и не подключает этот роутер.
`client.py` также его не подключает. Frontend вызывает эти адреса из вкладки
«Статистика», но соответствующие обработчики не зарегистрированы.
При раздаче статики ошибочный GET может попасть в статический обработчик,
поэтому конкретный HTTP-ответ зависит от запуска. Дефект подтверждён статически.
Существующие backend-тесты обращаются к этим маршрутам и должны выявлять проблему
при запуске. UI-тесты analytics.spec.ts подменяют API и сами её обнаружить не могут.

### Аналитика разделена на два независимых хранилища

- PostMetrics: последнее известное измерение каждого показателя для постов приложения.
- TaskRun.metrics: снимок Telegram-канала за последние семь дней, включая внешние посты.
- collect_metrics не записывает полученные значения в PostMetrics.
- Рекомендации по расписанию используют последний успешный statistics-запуск компании,
  а не показатели из PostMetrics. При нескольких каналах это может быть другой канал.

Нужно связать каналы, сообщения и измерения, сохраняя происхождение данных.
Нельзя складывать одинаковые публикации из двух потоков как разные посты.

### Недостаточно истории для динамики

PostMetrics хранит последние значения, не ряд снимков. Из них нельзя восстановить
прирост просмотров за прошлую неделю или корректно сравнить две недели.
Снимки TaskRun сохраняются, но их семидневные окна могут перекрываться.
Текущая логика отмечает это в comparison_note. Нужны явные даты, окна сравнения
и состояние «Недостаточно истории» вместо неподтверждённых процентов роста.

### Разные определения показателей

- Статистика постов: доля реакций = реакции / просмотры × 100%.
- Telegram-отчёт: вовлечённость = (реакции + пересылки) / просмотры × 100%.
- Эти величины нельзя показывать как один и тот же ER.
- Сумма просмотров постов не является уникальным охватом.
- Фильтр 7/30/90 дней сейчас выбирает даты публикаций, а не просмотры, полученные в эти дни.
- Сводка постов ограничена последними 200 публикациями, AI-анализ — 50.
- Ряд публикаций по дням сейчас привязан к МСК, задачи используют собственный часовой пояс.

### Анализ рынка пока представляет собой текст

Поиск ограничен пятью источниками и последним месяцем. Нет карточек конкурентов,
структурированных результатов, отдельных настроек географии, истории стратегии
или проверки гипотез. Веб-поиск даёт публичные сведения, не закрытые показатели
продаж, рекламных бюджетов и внутренней аналитики конкурентов.

### Отчёты и маршрутизация запросов

Успешный аналитический TaskRun сохраняется в БД, но execute_run не отправляет
его результат сотрудникам компании в Telegram. Ошибки уведомляют оператора.
Нужны получатели и ссылка на отчёт в Mini App.

Чат-агент ориентирован на создание постов; слова «подготовь», «придумай», «контент»
могут инициировать принудительную генерацию поста. Новые сценарии исследования
и гипотез следует запускать явно через кабинет; поддержку свободных аналитических
запросов в боте нужно реализовывать отдельной маршрутизацией.

### Документация не полностью соответствует коду

README ещё указывает сбор статистики и анализ конкурентов среди отсутствующих функций,
хотя часть уже добавлена. В docs/openapi.yaml многие будущие API помечены proposed,
включая аналитику, стратегию и конкурентов. Это планы, а не работающие обработчики.
Контракт предложенного /api/analytics/posts отличается от фактического кода.

За пределами текущего этапа: реальные адаптеры VK/MAX, мониторинг обращений,
генерация коротких видео и проверка подключения существующего аккаунта ChatGPT.
В частности, ChatGPTAccountProvider выбрасывает NotImplementedError — критерий 12
не закрыт этим кодом. Это вывод о реализации, не проверка доступных способов подключения.

## 6. Предложение интерфейса для согласования

В кабинете компании добавить рабочий раздел «Маркетолог», доступный сотрудникам
и администратору. Не открывать сотрудникам настройки команды, секреты и подключения.
Существующие технические разделы сохранить для администратора.

| Экран | Содержимое и действия |
|---|---|
| Обзор | Показатели, выбранный канал и период, свежесть/покрытие, ключевые выводы, следующие действия |
| Рынок | Ниша, география, продукт, запуск анализа; тенденции, возможности, риски, источники и дата |
| Конкуренты | Список сайтов и Telegram-каналов; позиционирование, темы, форматы, активность и доступные показатели |
| Контент и аналитика | Посты, метрики, сравнение форматов/рубрик, лучшие материалы и основания выводов |
| Гипотезы | Проверяемые предложения, фактические основания, KPI, срок, статус, результат эксперимента |
| Стратегия и план | Цели, аудитории, преимущества, каналы, рубрики, план тем и переход к подготовке поста |
| Отчёты | Архив, период, показатели, выводы, рекомендуемые действия; запуск сейчас и расписание |

Заявки и продажи — блок обзора/отчёта со статусом «Источник не подключён».
Не показывать нули, выручку, конверсию, ROMI или причинную связь без исходных данных.

Карточка гипотезы: «что заметили» со ссылкой на посты/источники → «что изменяем» →
«какую метрику проверяем» → «критерий успеха» → «период проверки» → «результат».
Любые ожидаемые проценты обозначать как целевое значение эксперимента, не прогноз.
Статусы: предложена, в работе, подтверждена, не подтверждена, недостаточно данных, архив.
Действие «Подготовить пост» создаёт материал, проходящий существующее согласование.

При пустых данных объяснять, что подключить или собрать. Ошибки источников,
устаревший анализ и неполная выборка должны быть видны. Сохранённый результат
открывается без повторного платного вызова AI. Длинные операции выполняются в очередях.
Мобильный интерфейс пригоден для Telegram Mini App.

## 7. Предложение технического объёма

1. Исправить подключение API аналитики и проверить существующие backend-тесты.
2. Объединить чтение доступных показателей в сервис аналитики компании/канала;
   добавить историю снимков, происхождение, покрытие и явные определения метрик.
3. Переиспользовать Task/TaskRun, очереди, расписания, лимиты, журнал, знания и LLM.
   Добавить запуск исследования/отчёта «сейчас» с отслеживанием статуса.
4. Добавить сущности конкурентов, исследований, гипотез, отчётов, стратегии и плана
   с company_id. Долгоживущие результаты и связи хранить в БД, не только в тексте AI.
5. Проверять структурированный ответ модели; расчёт показателей выполнять кодом.
   Текст модели не должен самостоятельно менять расписания, права и публикации.
6. Встроить рабочий раздел в существующую FSD-архитектуру и авторизацию.
7. Уведомлять выбранных получателей компании о готовом отчёте; оператору — сбои.
8. Актуализировать OpenAPI, описание возможностей и инструкцию настройки.

Проверки реализации: изоляция компаний и права; неизвестное против нуля;
сопоставимость периодов и формул; отсутствие двойного учёта; валидация AI-ответа;
сбой поиска и Telegram; сохранение после перезапуска; расписание и уведомления;
переход гипотеза → пост → согласование; сценарий сотрудника и мобильный экран.
Проверить UI с реальным backend, поскольку моки не проверяют регистрацию маршрутов.

## 8. Детали, ожидающие согласования

- Утвердить предложенные семь экранов и включение стратегии/контент-плана в первый этап.
- Предложение прав: сотрудник читает аналитику, запускает исследования, ведёт конкурентов
  и гипотезы, готовит предложения; администратор дополнительно управляет источниками,
  получателями/расписанием отчётов, утверждает стратегию и публикации.
- Предложение отчётности: еженедельно по понедельникам в 09:00 в выбранном часовом поясе,
  уведомление администратору компании; ручной запуск доступен из кабинета.
  До подтверждения автоматическая рассылка не включается.
- Предложение выбора конкурентов: AI предлагает по нише и географии, пользователь
  подтверждает список; можно добавлять сайты/каналы вручную.
- Для предметной демонстрации нужна тестовая компания, её рынок/география и канал.
  Разработку структуры и пустых состояний можно выполнять без этих сведений.

## 9. Критерий готовности нашей части

Сотрудник открывает свою компанию, видит реальные доступные показатели с датами,
запускает анализ рынка и подтверждённых конкурентов, получает выводы с источниками,
создаёт измеримую гипотезу и предложение контента. Администратор согласует материал.
Отчёт по расписанию сохраняет конкретные показатели, выводы и действия и сообщает
о готовности в Telegram выбранному получателю. При нехватке данных система сообщает
об этом явно. Ни один пользователь не получает данные другой компании.
