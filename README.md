# Автономный AI-маркетолог

Прототип для хакатона «Кибер 102»: Telegram-бот + Mini App + Core API с AI-агентом.

```
Telegram (бот, Mini App) ──► Core API (FastAPI)
                              ├─ auth: подпись initData, роли, изоляция по company_id
                              ├─ agent: LLM-провайдер (stub | openai | chatgpt_account)
                              ├─ workflow: автомат статусов согласования
                              ├─ tasks: регулярные задачи и статистика Telegram
                              ├─ content-plans: генерация планов на 1–31 день
                              ├─ scheduler: регулярные задачи и отложенная публикация
                              └─ platforms: telegram (vk, max — добавляются в REGISTRY)
```

## Запуск локально

```bash
cd backend
python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env           # Windows: copy .env.example .env
uvicorn app.main:app --reload
```

Заполните `backend/.env` по образцу `backend/.env.example`. Минимум для бота: `BOT_TOKEN`, `ADMIN_IDS`.
Без `PUBLIC_URL` бот работает через long polling. С `LLM_PROVIDER=stub` внешних вызовов нет —
можно проверить весь сценарий без ключей.

Mini App: `cd frontend && npm install && npm run dev` (Node.js 22+; для входа в браузере без Telegram
задайте `VITE_DEV_USER=<id>` и `DEV_AUTH_BYPASS=true` в backend/.env — только для разработки).
Для работы внутри Telegram нужен публичный HTTPS-адрес (cloudflared/ngrok или деплой) → `PUBLIC_URL`.
`npm run build` собирает Mini App в `frontend/dist`, и backend отдаёт её тем же сервисом.

Для очередей, повторов и распределённых блокировок нужен Redis: `REDIS_URL=redis://localhost:6379/0`
(например, `docker compose up -d redis`). Без него задачи выполняются в том же процессе одной попыткой;
отложенные публикации и регулярные задачи подхватывает планировщик приложения.
Файлы контекста организаций хранятся в Yandex Object Storage — задайте `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
`S3_SECRET_ACCESS_KEY` (ключи только в `.env`, в репозиторий они не попадают).

## Возможности

### Диалог и результаты ИИ

Сотрудники работают с ИИ в Telegram и в кабинете; администратору компании доступна вкладка «ИИ».
Личная переписка синхронизируется между интерфейсами. ИИ использует её и общие материалы, задачи и решения
компании; переписка других сотрудников недоступна. Даты и относительные запросы («вчера») трактуются в UTC.
Старые сообщения без автора сохраняются в БД, но не включаются в личную память.

Каждая операция ИИ имеет постоянную запись выполнения. После успеха или ошибки итог сохраняется в истории
и отправляется инициатору в Telegram. Регулярные задачи уведомляют автора, а старые задачи без автора —
администраторов компании. Подготовленный материал по-прежнему требует согласования перед публикацией.

- `POST /api/agent/runs` — `{text, parent_run_id?, kind?: "message"|"revise"|"image", post_id?, version?}`, ответ `202`.
- `POST /api/agent/runs/reference` — multipart: `text`, один файл `reference`, необязательный `parent_run_id`.
- `GET /api/agent/runs` и `GET /api/agent/runs/{id}` — личные выполнения и их состояния.
- `GET /api/agent/messages?before=<id>&limit=50` — история, `{items, next_cursor}`.

Старые синхронные `/api/agent/message` и `/api/agent/message/reference` сохранены.
Новые таблицы и поля добавляются при старте приложения; данные не удаляются. Требуется перезапуск backend.
Планировщик восстанавливает задания, не дошедшие до очереди, и повторяет доставку из постоянного outbox.
Прерванное выполнение с уже сохранённым результатом не генерирует второй материал. Незавершённые работы
после 16 минут получают итог о прерывании, если нельзя подтвердить сохранённый результат.
Прогресс отправки длинного ответа сохраняется по частям. При аварии между приёмом сообщения Telegram
и фиксацией отправки в БД одна часть может прийти повторно: Telegram не предоставляет идемпотентный ключ отправки.

Кабинет проверяет выполняющиеся задачи каждые 3 секунды, остальную историю — каждые 15 секунд.

### Задачи по расписанию

Сотрудники и администратор компании создают задачи во вкладке «Задачи»; оператор сервиса только
просматривает их в кабинете выбранной компании. Каталог: подготовка поста, анализ рынка (Tavily),
рекомендации по контенту и сбор статистики Telegram-канала. Расписание — каждые N часов (от 60 минут),
ежедневно, по дням недели или разово. Часовой пояс IANA сохраняется в задаче, моменты исполнения — в UTC:
пропущенное из-за перехода на летнее время время переносится на ближайшую допустимую минуту,
повторяющееся выполняется один раз.

- Для поста время означает публикацию: материал готовится за 24 часа и уходит на согласование.
  Если время публикации уже прошло или одобрение пришло позже, требуется новое время.
- Остальные задачи присылают результат автору; задачи без автора — администраторам компании.
  История запусков хранит результат, источники, метрики и ошибки. Пауза останавливает выполнение;
  удаление отменяет будущие запуски, но сохраняет созданные посты и назначенные публикации.
- Анализ рынка требует `TAVILY_API_KEY`; без него задача завершается понятной ошибкой.
- Статистика использует пользовательскую сессию Telethon: администратор компании подключает аккаунт
  (номер, код, при необходимости пароль 2FA) и выбирает каналы. Нужны `TELEGRAM_API_ID`,
  `TELEGRAM_API_HASH` и постоянный `SECRET_KEY`; сессия хранится в БД зашифрованной, код и пароль
  не сохраняются. Каналы для аналитики не становятся адресатами публикаций.
- API: `GET /api/tasks/catalog`, `GET|POST /api/tasks`, `GET|PATCH|DELETE /api/tasks/{id}`,
  `GET /api/tasks/{id}/runs`; подключение Telegram — `/api/telegram-analytics/*`.

### Контент-планы

Планы находятся во вкладке «Профиль» и общие для компании: сотрудник и администратор создают и правят,
оператор сервиса только просматривает. Форма: название, начало и конец периода включительно (1–31 день),
1–10 постов в день и пожелания. По умолчанию — сегодня и следующие 6 дней, один пост в день.
Генерация учитывает знания и бренд компании, идёт в фоне по одному заданию на день через очередь
`ai-generation`; прогресс и ошибки видны в плане, повторяются только неготовые дни.

- Описание и тему задачи можно изменить, перенести задачу внутри периода, добавить и удалить.
  Конкурирующая правка со старой версией возвращает 409. Удаление мягкое, созданные посты сохраняются.
- Готовый день не перезаписывается, включая ручные правки. Исчерпание бюджета останавливает генерацию
  до пополнения и ручного повтора; временные сбои повторяются до трёх раз.
- По задаче плана создаётся пост в «Постах» или из самого плана. Пост сохраняет связь с задачей
  и текст задания; генерация проходит обычные лимиты, проверку бренда и согласование.
  Дата плана не назначает время публикации автоматически.
- API: `GET|POST /api/content-plans`, `GET /api/content-plans/{id}`,
  `POST /api/content-plans/{id}/retry`, `POST /api/content-plans/{id}/items`,
  `PATCH|DELETE /api/content-plans/items/{id}`. Таблицы `content_plans`, `content_plan_days`,
  `content_plan_items`; в `posts` — nullable-поля `content_plan_item_id` и `content_plan_prompt`.

### Пост по изображению-референсу

Отправьте боту одно фото (или PNG/JPEG/WebP файлом, до 10 МБ) и напишите
задание для поста в подписи. Например: «Создай пост про новую услугу.
Для картинки возьми палитру и композицию референса, замени заголовок на …».
Альбомы не поддерживаются. Референс передаётся генератору изображений через
`/v1/images/edits`; текстовая модель получает задание без изображения.
Референс не сохраняется в истории чата и не отправляется в последующих запросах.

Для API: `POST /api/agent/runs/reference` — multipart-поля `text`, один файл `reference`,
необязательный `parent_run_id`. Синхронный `POST /api/agent/message/reference` сохранён.

### Статистика публикаций и рекомендации

Во вкладке «Статистика» доступны периоды 7/30/90 дней и всё время, показатели
постов, сводка и график числа публикаций по дням (МСК). Сводка использует до
200 последних публикаций периода и показывает покрытие каждого показателя.
При публикации сохраняются фактическое время и числовой ID канала.
Старые посты без известной даты доступны в периоде «Всё время»; дата создания
черновика не подменяет дату публикации.

Telegram автоматически присылает абсолютные счётчики анонимных реакций, если
бот — администратор канала. Обновление `message_reaction_count` включено для
webhook и polling. Повторы и устаревшие события не удваивают показатели.
Счётчики относятся к основному опубликованному сообщению: если изображение
и длинный текст отправлены отдельно, учитывается сообщение с текстом.
Если канал публикуется отдельным ботом, его обновления также должны поступать
в приложение; настройка токена только для отправки не подписывает основной
бот на события другого бота.

Просмотры, пересылки и комментарии администратор компании вносит из Telegram
вручную: Bot API не предоставляет чтение этих счётчиков. Неизвестное значение
показано как «—», измеренный ноль — как 0. Пустые поля при сохранении не
меняют прежние показатели. Каждое измерение содержит время и источник.

Доля реакций = реакции / просмотры × 100%, если просмотров больше нуля
и показатели измерены с разницей не более 24 часов. Общая доля — отношение
сумм по этим же постам, а не среднее процентов. Просмотры не означают уникальный
охват. Автоматические рекомендации сравнивают только посты одного канала с
известной датой и минимум 100 просмотрами, при наличии хотя бы трёх измерений.
Для корректных экспериментов собирайте счётчики через одинаковый срок после
публикации: рекомендации формулируются как гипотезы, не причинные выводы.

AI-анализ запускается администратором компании по кнопке после измерения хотя
бы трёх постов. Использует настроенную текстовую модель, до 50 последних
измеренных постов, бюджет и лимиты компании. Результат сохраняется; повтор без
изменения данных возвращает сохранённый результат без нового LLM-запроса.
При изменении данных показывается отметка об устаревании. Расписания и
публикации анализ не меняет. Оператор сервиса может просматривать статистику,
но не вносить показатели и не заказывать AI-анализ от имени клиента.

API: `GET /api/analytics/posts?days=30` (7/30/90 или 0 — всё время),
`PUT /api/posts/{id}/metrics` (частичный JSON со счётчиками; необязательный
`observed_at` с часовым поясом), `POST /api/analytics/posts/recommendations` (`{"days":30}`).
Новые таблицы и колонки добавляются существующей мини-миграцией при старте.

## Тесты

### Backend

```bash
cd backend
source .venv/bin/activate      # Windows: .venv\Scripts\activate
python -m pytest
```

Проверка контент-планов на отдельной PostgreSQL-базе:

```bash
CONTENT_PLAN_TEST_DATABASE_URL=postgresql+asyncpg://user:password@localhost/testdb \
  pytest tests/test_content_plans_postgres.py -q
```

### Frontend

```bash
cd frontend
npm ci
npm run build
npx playwright install chromium
npm run test:e2e
```

Браузерные тесты работают с моками API и проверяют вкладки, формы, валидацию, мобильную вёрстку
и ограничения ролей.

Покрывают: публикация только после согласования и привязка одобрения к версии, отсутствие дублей,
изоляция компаний и ролей, неразглашение токенов; постоянные выполнения ИИ, outbox и восстановление
после сбоя; контент-планы, расписания и переходы времени, статистику и рекомендации, S3/Redis.

## Подключение новой компании (без кода)

1. Откройте Mini App под администратором (ID в `ADMIN_IDS`) → «Компании» → «Создать».
2. Выберите компанию → добавьте знания (описание, продукты, аудитория).
3. «Канал для публикаций»: укажите `@channel`; бот должен быть админом канала.
4. «Приглашение» → отправьте ссылку согласующему; он переходит по ней и привязывается к компании.

## Деплой

`docker compose up -d --build` поднимает Postgres, Redis и приложение; фронтенд собирается в образ
и отдаётся тем же сервисом. Нужен `backend/.env` (см. `docker-compose.yml`). Задайте `PUBLIC_URL` —
webhook ставится автоматически; если Telegram недоступен по webhook, используйте `BOT_MODE=polling`.
Для production сохраняйте `SECRET_KEY` между деплоями, иначе зашифрованные Telegram-сессии станут
недоступны. Подробности, секреты и откат — `docs/deploy.md`.

## Что не реализовано (честно)

- Подключение через аккаунт ChatGPT (`llm/chatgpt_account.py` — заготовка, критерий №12 требует проверки).
- Адаптеры VK и MAX; мониторинг комментариев (обработчик очереди `moderation` готов, источника сообщений нет).
- Автоматическое чтение просмотров, пересылок и комментариев через Bot API: администратор вносит их вручную.
  CRM, заявки и продажи не подключены.
- Парсинг сайтов в базу знаний (файлы TXT/MD/CSV/JSON/HTML/PDF/DOCX загружаются в Yandex S3 и разбираются).
- Миграции БД (Alembic): таблицы создаются мини-миграцией при старте.
